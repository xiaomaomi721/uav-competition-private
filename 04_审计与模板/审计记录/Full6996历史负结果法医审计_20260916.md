### 位置 5.1：LR schedule 是按「成功更新数」而非「数据迭代数」推进的

主线 `trainer.py` L664-670：

```python
optimizer_updated = not (use_amp and float(scaler.get_scale()) < float(scale_before))
if optimizer_updated:
    optimizer_update_count += 1
    ...
    scheduler.step()          # ← 只在成功更新时推进
else:
    skipped_optimizer_steps += 1
```

验算：末步记录 LR `2.228667e-08`；`6e-5 × (1 − 69971/69997) = 2.2287e-08` ✓（69971 = 更新数），而 `6e-5 × (1 − 69997/69997) = 0`。

**但 Stage23 完全一样**：56000 步 / 55980 更新 / 20 跳步，末步 LR `2.142857e-08` = `6e-5 × (1 − 55980/56000)` ✓。

→ **这是主线固有行为，不是 Full6996 引入的偏差。** 偏差量级：Full6996 26/69997 = 0.037%，Stage23 20/56000 = 0.036%，**两者一致，不构成混淆**。记录在此以免日后被误判为新发现。

#### 但这不构成与 Stage23 的对照不对称（已核验）

我一度怀疑"Full6996 用裸末步、Stage23 用精选 best，两边口径不同"。**该怀疑不成立**：

```
Stage23 best_miou.pt : step = 56000  best_miou = 0.8109861457370224
Stage23 last.pt      : step = 56000
Stage23 metrics.json : best_step = 56000
```

Stage23 的 best **就是它的末步**（验证 mIoU 到最后一刻仍在上升，best_step = 末步 = 56000）。
两个 arm 因此都是"各取末步"，**口径一致**。

#### 真正值得注意的是轨迹形状不同

| arm | 末步零偏置 | 次优零偏置 | 形状 |
|---|---:|---:|---|
| Stage23（5597, 56000 步） | **0.678023** | —（best = 末步，无更早的可比点） | 到末步仍在升 |
| Full6996（6996, 69997 步） | 0.670438 | 0.675388 @ 65000 | **末段回落 0.495pp** |

- 末步对末步（进度完全匹配）：0.670438 vs 0.678023 = **−0.5602pp**
- 最优对最优可得点：0.675388 vs 0.678023 = **−0.2635pp**（但 65000 是 93% 进度，与 100% 不完全匹配）

唯一残留的开放点是：**55000 与 60000 从未出包，Full6996 的峰值区间未被完整覆盖。** 若峰值落在 60000–64000 之间，现有数据无法排除。

| **`status: PASS` 汇总** | **不能** | **不可归因，已从证据中移除** |

**结论**：**对 preflight 文件中仍可见且可复核的字段，失效范围目前有限；未存档的检查项范围未知。**

不能写"preflight 失效范围有限"——原五项不可恢复，**逻辑上无法证明未知部分也有限**。唯一成立的表述是上面这句。
