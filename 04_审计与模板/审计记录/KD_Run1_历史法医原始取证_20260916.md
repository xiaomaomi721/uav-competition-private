## E. 损失数学（CPU 独立重算）

我把 `_kd_train.py` 的 `soft_kd_loss` 导入（`CUDA_VISIBLE_DEVICES=''`，未用 GPU），对随机输入与一个**完全独立手写的重算**逐项比对：

```
loss match  : True   0.4516301155090332  vs  0.4516301155090332
wmean match : True   0.38277193903923035
w at uniform(1/8) = 0.3
w at onehot(1.0)  = 1.0
KL(q||p) forward, non-negative: True
T^2 factor present: True
```

逐项核对：

| 项 | 实现 | 判定 |
|---|---|---|
| 上采样方向 | student logits → teacher 网格（`F.interpolate` bilinear） | 与 `src.inference.evaluate_model` 同向 ✓ |
| KL 方向 | `(log_q.exp() * (log_q - log_p))` = **KL(q‖p)**，q=teacher | 前向 KL，非反向 ✓ |
| 温度 | 仅作用于 `log_p = log_softmax(student/T)`；q 不除 T | 与 Hinton 式 `T²·KL(q‖softmax(z/T))` 一致 ✓ |
| T² 因子 | 存在 ✓ | |
| 权重 w | `w_min + (1−w_min)·(p_max − 1/C)/(1 − 1/C)` | 均匀分布→0.3，onehot→1.0 ✓ |
| w 裁剪 | `clamp(w_min, 1.0)` ✓ | |

**核心 KD 数学没有发现错误。**

一个术语上的精确化（不影响数值）：标准 Hinton KD 的形式是 `T²·KL(p_student‖p_teacher)`。本实现取的是**反向** KL `KL(teacher‖student)`。两者都合法，但行为不同——**前向 KL（本实现）是 mode-covering**，会惩罚"教师在的地方学生给低概率"，倾向于让学生覆盖教师的支撑集；反向 KL 是 mode-seeking。这里写下来供日后解释轨迹用，不作为缺陷。

## F. ⚠️ **kd_every 实际暴露率是文档的 2 倍**

### F.1 代码事实

```python
417      for step in range(max_steps):
423          do_test = (step % int(args.kd_every) == 0)     # ← 在 accum 循环之外
425          for micro in range(accum):
...
442              kd_term = None
443              if do_test:                                 # ← 每个 micro 都进
444                  tb = next(test_iter)
...
454                  kd_term = args.lambda_kd * kd
462              total = ce if kd_term is None else (ce + kd_term)
463              scaler.scale(total / accum).backward()
```

`do_test` 判定在 `for micro in range(accum)` **之外** → 在 KD 步上，**两个 micro 各消耗一个 test 批**。

### F.2 实际消耗

```
grad_accum = 2, kd_every = 2, max_steps = 8000
KD 步数（0-based 偶数）= 4000
每个 KD 步消耗 test 批 = 2
→ 累计 test 批 = 8000
test batches/epoch = 250          （日志首行：test batches=250）
→ test1 被遍历 = 8000 / 250 = 32 epoch
→ 图像级 = 8000 × 2 / 500 = 32 遍
```

### F.3 文档值

`KD_META.json`：

```json
"kd_every": 2,
"sampling_ratio_note": "1 test-KD batch per kd_every optimizer steps"
```

按此字面：1 批 / 2 步 × 8000 步 = **4000 批 = 16 epoch**。

### F.4 判决

> **实际 test1 暴露是文档记载的 2 倍（32 epoch vs 16 epoch）。**

**但总体 real : test 比例没有错。** 完整核算（见 §F.7）：

```
optimizer steps        = 8000
real  micro-batches    = 8000 × 2 = 16000
KD optimizer steps     = 4000
test  micro-batches    = 4000 × 2 =  8000
real : test            = 16000 : 8000 = 2.0000 : 1
```

`_kd_launch.sh` 注释写的 **"2 real : 1 test" 是正确的**，指的是总体 micro-batch 采样比。

`_kd_launch.sh` 的两句注释都不算错，只是粒度不同：

```bash
# KD_EVERY=1 -> one test soft-KD batch per optimizer step (higher target exposure)
# KD_EVERY=2 -> GT-heavy (2 real : 1 test) -- the agreed default
```

第一句是**每 optimizer step** 粒度（KD_EVERY=2 时确实是 1 批/步），第二句是**全程总量**粒度（2:1）。两者在 accum=2 下同时成立。

### F.5 ⚠️ 我方此前两处错误（自我纠正，均已撤回）

**错误一（漏乘 accum）：**

我在本审计开始前曾写：

> "KD 批的处理已核验：KD 批在 0-based 偶数步触发，4000 总计 = 250 × 16 ✓"

**这是错的。** 4000 是 **KD 步数**，不是 KD 批数；漏乘了 accum。**实际批数是 8000，遍历 32 遍。**

**错误二（口径混淆，把"每步 2:2"当成"总体 1:1"）：**

我在第一版审计中写：

> "但代码在 accum=2 下给出的是**每一步 2 批**，实际比例是 **1 real : 1 test**，不是 2:1。"

**这也是错的。** 我按**每 optimizer step** 比（2 real : 2 test = 1:1），而 exposure ratio 的正确口径是**全程总量**（16000 : 8000 = 2:1）。同一现象，我选错了口径并据此下了"实际 1:1"的判决。

**GPT 更正**（2026-09-16）：*"2 real : 1 test 这个总体采样比例其实是对的。真正错误的是 KD_META.json…把 test1 的实际 exposure 低估了 2 倍。"*

**修订后结论：**

> **实际总体 real:test micro-batch exposure 仍为 2:1，与 launch 注释一致；但 `KD_META.json` 低估了 test1 的累计 epoch exposure 2 倍（实际 32 而非 16）。loss weighting 本身未发现因此翻倍。** 这是 **provenance / 文档错误**，不是算法 bug。

### F.6 但这一切不改变 `INVARIANT 2`，λ 未被静默缩放

代码注释声称"one optimizer step optimises exactly `L = CE + lambda*KD`"。逐项验算：

```
grad_contrib = (ce₀ + λ·kd₀)/2 + (ce₁ + λ·kd₁)/2 = mean(CE) + λ·mean(KD)   ✓
```

**注记本身是正确的**——除以同一个 `accum` 保证了 λ 不被静默缩放。

针对"两个 KD micro 是否把 λ=0.35 静默变成 0.70"的专项核验：

```
KD step   : d/dCE = 1.0000   d/dKD = 0.3500      <- 两个 micro 各带 /accum，累加后取平均
nonKD step: d/dCE = 1.0000   d/dKD = 0.0000
=> effective lambda on a KD step = 0.3500  (ratio to 0.35 = 1.00)
```

**两个 KD micro 只是组成该 optimizer step 的平均 KD 梯度，λ 保持 0.35，未被翻倍。**

时间平均意义上，KD 项在全程的有效权重是 `0.35 × 4000/8000 = 0.175`——这是"一半的步带 KD"的自然结果，不是实现缺陷。

## G. AMP / dtype

### G.1 事实


`GradScaler` 未覆盖任何参数 → 走 torch 默认（`growth_interval=2000`、`growth_factor=2.0`、`backoff_factor=0.5`）。

### G.2 与主线的差异

主线 `src/trainer.py` L664-670：

```python
optimizer_updated = not (use_amp and float(scaler.get_scale()) < float(scale_before))
if optimizer_updated:
    optimizer_update_count += 1
    scheduler.step()          # ← 只在成功更新时推进
else:
    skipped_optimizer_steps += 1
```

KD **没有**这一层判定：`scaler.step()` / `scaler.update()` / `scheduler.step()` 无条件调用。

### G.3 实际影响评估（不要把两者混为一谈）

- **模型侧无损坏**：torch 的 `scaler.step(optimizer)` 在检测到 inf/nan 时**内部跳过** optimizer 更新（它自己 `unscale_` 时发现了就会 skip），参数不会被污染。
- **区别在记账与 LR**：KD 不计数、不报告 skip；若真发生 skip，`scheduler.step()` 仍会推进，LR 会比"按成功更新数"的方式略快一点点。
- **证据**：`kd_run1_s62init.log` 中**所有** `step=` 行的 `ce=` / `kd=` 均为有限值；`COMPLETED.json` 正常写出；末步 `local_miou` 有限。**没有观察到任何 skip 的直接证据。**
- **但也没有反向证据**。KD 的日志格式不打印 scale 轨迹，**无法排除**少量 skip。若 skip 比例与 s62 的 23/68600 = 0.034% 同量级，则 8000 步约 3 次——LR 偏差量级 3/8000 = 0.04%，**可忽略**。

### G.4 LR 调度：按数据迭代，不是按更新次数

实测对照（日志 vs 公式）：

```
日志 step=7951/8000  →  lr=1.838e-07
公式 3e-5 × (1 − 7951/8000) = 1.8375e-07   ✓
```

`LambdaLR(lambda s: max(0, 1 − s/8000))`，`s` 即数据迭代计数，且 `max_steps` 传的是 8000（与实际步数一致，**未发生 Stage23 式的"预算按 epoch 重标定"**）。

s62 的 LR 是 6e-5，KD 是 3e-5 —— **减半**，符合"微调"定位。

## H. init / optimizer / scheduler 的实际装载范围

`load_model_checkpoint(model, Path(args.init_checkpoint), device)` 只装载 **model 权重**。

KD 侧全部**新建**：

```python
optimizer = torch.optim.AdamW(model.parameters(), lr=3.0e-5,
                              weight_decay=config.optimizer.weight_decay)   # = 0.01
scheduler = torch.optim.lr_scheduler.LambdaLR(optimizer, lambda s: max(0, 1 − s/8000))
scaler    = torch.amp.GradScaler("cuda", enabled=True)
```

→ **没有**继承 s62 的 AdamW 动量、没有继承 s62 的 LR 位置、没有继承 GradScaler scale。

这是**正确**的做法（s62 的 optimizer 状态对应 6e-5 的 poly 尾巴，硬搬进来会冲突），但它意味着 **KD 的起点在优化器意义上不是"继续 s62"，而是一次冷重启动的微调**。解释轨迹时必须带上。

## M. 代码与监督基线的差异

### M.1 增强：KD 重新实现了一份，且**缺 color jitter**

`_kd_train.py` 自己实现了 `KDDataset._aug_params` / `_apply_geom`，**没有**走主线的 `src.transforms.TrainTransform`。

实测 KD 实现的几何增强：

```python
def _aug_params(self, rng):
    return dict(
        hflip=rng.random() < 0.5,
        vflip=rng.random() < 0.5,
        rot=rng.randrange(4) if rng.random() < 0.5 else 0,
    )
```

与主线 `src/transforms.py` L171 **逐字面等价**：

```python
rotate_k=rng.randrange(4) if rng.random() < float(self.config.get("rotate90_probability", 0.5)) else 0
```

`_apply_geom` 的 flip/rot90 语义与 `apply_geometric_ops` 逐行一致（`np.flip(axis=1)` 水平 / `np.flip(axis=0)` 垂直 / `np.rot90(k)`），且 image 与 aux 由**同一个 `p`** 驱动，非原地操作，末尾 `ascontiguousarray`。**几何增强无错位、无缺陷。**

**但颜色侧完全缺失**：

```
grep -c 'jitter|brightness|hue|contrast' _kd_train.py  →  0
```

主线 stage62 配置（`transforms.color_jitter`）：

```yaml
color_jitter:
  probability: 0.5
  brightness: 0.1
  contrast: 0.1
  saturation: 0.1
  hue: 0.02
```

> **KD 训练全程没有颜色抖动**，而 s62 是在 p=0.5 的颜色抖动下训练的。

这是一处**可观察的 regime 差异**：学生在 KD 中见到的输入分布比它被训练时所处的分布更"干净"。是否足以解释本地掉分，**本审计不裁定**，只记录事实。

### M.2 crop：缺失但为 no-op（已核验，两轮都成立）

`_kd_train.py` 的 `_aug_params` / `_apply_geom` 里**没有 crop**。`apply_geometric_ops` 在第 99 行被 import、第 23 行被 docstring 提及，但 `grep` 确认**从未被调用**（死 import）。

我此前怀疑这会造成空间错位。**核验后否定**：test1 全部为 1024×1024，`config["crop_size"] = 1024`，主线 `RareClassCropper._random_origin` 在 `crop_size == 图像尺寸` 时返回 `(0, 0)` → **rare crop 是 NO-OP**。学生侧同样。**无错位。**

（真实训练集也是 1024²。该结论对 real 分支同样成立。）

### M.3 CWFA：起始点被改写

```python
config["cwfa"]["start_step"] = 1
set_cwfa_active(model, True)
print("CWFA forced ACTIVE for all KD steps (p=0.3, eps=4.0)")
```

| | s62 主线 | KD |
|---|---|---|
| `cwfa.start_step` | 28001 / 70000 = **40%** | **1** = 0%（全程） |

代码注释给出的理由是："so the student trains under the same regime it will be evaluated in (the s62 checkpoint itself was produced with CWFA active)"。

**验证时 CWFA 是关闭的**（`src/cwfa.py` forward 有 `not self.training` 守卫）：

```python
# Validation/inference must remain exactly clean.
if (not self.training or not self.enabled or not self.active
        or self.probability <= 0.0 or self.epsilon == 0.0):
    return features
```

→ `local_miou` 是**干净测量**，未受 CWFA 污染 ✓（这是一个正面确认）

但这同时说明注释里"evaluated in"的理由**不成立**：评估时 CWFA 根本不生效，学生评估时处于 CWFA-OFF regime，训练时却是 CWFA-ON 全程。**训练/评估 regime 是不一致的**（虽然偏差方向与注释所暗示的相反）。

## N. 三层结论

### N.1 第一层：实现正确性 —— **核心无错，三处偏离**

**验证正确（经独立重算或逐行对照）：**

| 项 | 方法 | 结果 |
|---|---|---|
| `soft_kd_loss` 数学 | CPU 独立重写比对 | 逐位一致 ✓ |
| KL 方向 / T² / w 公式 | 边界值检验（均匀→0.3，onehot→1.0） | ✓ |
| 几何增强 image↔aux 同步 | 逐行对照 `apply_geometric_ops` | 语义等价 ✓ |
| CE 上采样对齐 | 与 `evaluate_model` 同向同参数 | ✓ |
| 混淆矩阵累加 | 全局累加，批大小无关 | ✓ |
| 教师 SHA ×3 | 逐位核验 | ✓ |
| student init SHA | 逐位核验 | ✓ |
| cache 完整性 | 500 文件全扫，NaN/Inf=0 | ✓ |
| 归一化一致性 | 有 `clamp_min + renormalize` | ✓ |
| `INVARIANT 2`（λ 不被静默缩放） | 逐项验算 | 成立 ✓ |
| CWFA 不污染验证 | `not self.training` 守卫 | ✓ |

**发现的三处偏离（按重要度）：**

1. **（F）`kd_every` 实际暴露是文档的 2 倍** — 32 epoch vs 文档 16 epoch。`do_test` 在 accum 循环外。**不是损失错误，是文档/实现不一致，且实际比设计更激进。**
2. **（M.1）缺失 color jitter** — KD 无任何颜色抖动，s62 有 p=0.5。训练 regime 与 s62 不一致。
3. **（G）AMP skip 处理弱于主线** — 无 skip 计数、`scheduler.step()` 无条件。无观察到 skip 的证据，但无法排除；量级可忽略（§G.3）。

外加一处**非缺陷但需记录**：`apply_geometric_ops` 是死 import（§M.2）。

### N.2 第二层：实验设计归因强度 —— **弱**

- **无 λ=0 匹配对照**（§J）→ ΔZ 无法拆解为"KD 贡献"与"短而冷的微调本身"
- **含 33% 自蒸馏成分**（§K）
- **同时变动 ≥5 个变量**（λ、GT epoch、test1 暴露、color jitter、CWFA 起始、LR）
- **本地 top-1 与线上 top-1 相反**（§L.4）→ 选点依据不可用

> 因此：**"KD Run1 未取得收益"是观测事实；"KD 机制对本赛题无效"不是本实验能支持的结论。** 本实验的设计无法把二者分开。

### N.3 第三层：榜单绑定强度 —— **C（顺序推断）**

- 8 个分数由**用户按提交顺序粘贴**；平台**从未产出**任何可绑定的回执（§I.4.3）
- `PLATFORM_RECEIPT_KD_Run1_20260915.json` 自己写明 `method: "positional, submission order 64-73"`、
  `source: "用户报告的 10 个平台分数"`、`caveat: "用户未逐个点名包名"`
- 支持证据仅为 8/8 的低-高交替结构性旁证
- **这是全项目统一基线**（36-42、BATCH01 等同级），非 KD 特有弱点
- 数值本身用户直接粘贴，可信；**score ↔ filename/SHA 的对应属推断**

### N.4 结论的适用边界

本次审计支持的是：

> **按现有绑定，KD Run1 这套具体配方未显示线上收益；暂未发现足以推翻该负结果的执行 bug；但发现了三处足以削弱"KD 机制无效"这一归因的配方偏离。**

三个分句的**证据等级不同，不得合并引用**：

| 分句 | 来源 | 强度 |
|---|---|---|
| 暂未发现足以推翻该负结果的执行 bug | 训练侧审计（数学、增强、SHA、cache、λ） | **强**，全部后验重新取证 |
| 发现了三处配方偏离 | 代码事实 + 日志 | **强**，逐行可复核 |
| 未显示线上收益 | 包→平台分数 | **弱一档**，顺序推断，无平台绑定（§I.4.6） |

本次审计**不支持**：

> ~~"KD 对本赛题无效。"~~
> ~~"软蒸馏没有信息来源。"~~（教师含 2 个外部来源 + test1 软分布）
> ~~"KD 把模型训坏了。"~~（本地到 8000 只剩 −0.0426pp，且在恢复；且无 λ=0 对照）

### N.5 历史定位（与 Stage65 的共性结论）

本次历史法医对 Stage65、Full6996、KD Run1 三个负结果的结论形状一致：

> **历史实验本身大体真的这么跑了；核心代码没有"写炸"；问题在于实验设计不足以支持后来那么强的路线否定。**

| 实验 | 实现正确性 | provenance | 归因强度 |
