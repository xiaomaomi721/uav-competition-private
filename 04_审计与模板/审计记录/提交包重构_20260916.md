# 提交包重构（2026-09-16）

## 一句话

**一个文件夹 `提交包/`，编号 001–111 全局连续，按状态分两个子目录，汇报成绩只报编号。**

## 结构

```
提交包/
├── README_先看这个.md
├── 包登记表.md          ← 编号 → 文件 → 是什么 → 分数（人看）
├── 待提交/   001–004    4 个
├── 已提交/   005–111    107 个
└── 清单与记录/
      _包登记表_20260916.json / .csv   （机器读，含 SHA256）
      _包分数总表_20260916.json
      _删除记录_20260916.json
      _预测级重复_20260916.json
      _去重记录_20260916.json
      平台回执 *.json、交接文档 *.md
```

## 删除分三层，每层独立证据

| 层 | 数量 | 判据 |
|---|---:|---|
| 1. 逐字节相同的冗余副本 | 56 | 同名同 SHA256 |
| 2. **预测内容相同的冗余包** | 14 | ZIP 不同，但 **500 张预测逐像素完全相同** |
| 3. 可再生缓存 / 空目录 | 39 项 | `__pycache__`、OneDrive 云占位空目录 |

**保留规则（按序）**：① 有平台分数的留；② 已提交的优先于未提交的；
③ 原件所在处优先。**没有一个是凭印象删的。**

## 第 2 层是怎么查出来的（本轮最有价值的一步）

前一轮只做了**字节级**去重，于是漏掉了一类：**同一个模型输出被重新打包成不同 ZIP**。
这次做了**预测级**指纹——把 ZIP 里 500 张 PNG 解码后拼起来取哈希，
与 PNG 编码无关，所以能抓到"换了个封装但内容一样"的包。

结果抓到 10 组、14 个冗余，其中最关键的一组是：

```
待提交/005_ZERO_stage66_best51800_TTA8.zip
   ==  已提交/038_core_s66_semeda_zero.zip      (500 张逐像素相同)
```

## 由此解决的一个悬案

之前反复卡住的问题——「历史 ZERO 补包 9 个里，7 个没回报分数，
是已交未回报还是没交？」——现在有了确定答案：

| 原包 | 结论 | 依据 |
|---|---|---|
| Stage59 52k ZERO / 56k ZERO / localbest ZERO / 52k FIXED8D | **早已提交过** | 与 `历史提交包/` 逐字节相同 |
| Stage66 best51800 ZERO | **已提交过** | 与 038 号预测逐像素相同 |
| Stage59 44k ZERO | **确实未交** | 无任何重复 |
| Stage66 52k / 56k ZERO | **确实未交** | 无任何重复 |

**所以真正要补交的只有 4 个，不是 7 个。**

## 顺带修正的一个我造成的错误

9-16 早先去重时，我在 19 组里**保留了描述名、删掉了带编号的名字**，
（例如保留 `s52000_R_TTA8.zip`，删掉 `10_stage59_s52000_TTA8only.zip`）。
这恰好破坏了"按编号汇报成绩"的用法。

已在 `清单与记录/_编号恢复映射_20260916.json` 中记录了完整的
「描述名 → 原编号名」映射，全部 18 组可回溯。
